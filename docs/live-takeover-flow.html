Live chat takeover: how a conversation flows

One example chat from start to end: the AI answers, a team member takes over, the AI stays silent, the chat is handed back. Companion to docs/live-takeover-plan.md.

2026-11-12 · Decisions applied: admins + editors take over · one site-wide "Team member" name · auto hand-back after 10 min · live chat only when conversation recording is on · per-tab conversation · free.

1. Who is involved 2. Full flow, step by step 3. What each side sees 4. What happens to a visitor message 5. AI mode ↔ Human mode 6. Polling: who asks, how often 7. What is saved in the database 8. Special cases 9. Future: one row per message

1. Who is involved

Three parts. The visitor and the team member never talk directly: every message goes through the WordPress server and is saved in the database. Each side asks the server "anything new?" every few seconds (polling).

Visitor widget

  • The chat bubble on the website
  • Keeps its conversation ID in the tab (sessionStorage)
  • Sends messages to /chat/ask
  • Asks /chat/live for team messages

WordPress server + DB

  • Knows each chat's mode: ai or human
  • In ai mode: search + AI answer
  • In human mode: just saves the message, no AI
  • Stores every message, so both sides can read it

Dashboard (Live chat tab)

  • Admin or editor, logged in to wp-admin
  • Sees active chats, opens one
  • Take over · reply · Hand back to AI
  • Sees real names; visitor sees only "Team member"

5. AI mode ↔ Human mode

Each conversation is always in exactly one mode. Only these four things change it.

6. Polling: who asks, how often

No open connections. Each side sends a short request on a timer. The server tells the widget the next interval in every answer, so we can tune it later without a new widget build.

Why not instant (WebSockets)?

Instant push needs a connection kept open per visitor. Shared hosting has only a few PHP workers, so a handful of open chats would block the whole site. Short requests finish in ~50 ms and free the worker.

What "online" means

Every widget poll stamps visitor_seen_at. The widget checks in at least every 60 s while the visitor is on the page. No check-in for 90 s → away dot. 3 min → "Visitor left the page" in the dashboard. Every dashboard poll by the agent in charge stamps agent_seen_at (used for auto hand-back).

How the widget gets only new things

The widget remembers the last row ID it got (after = 103). Next poll: "give me agent/event rows with id > 103" → gets 105, then 106. Its own messages it already has.

Unanswered questions stay clean

Only qa rows with "I don't know" count as unanswered. A question the team answered (visitor) is not an AI gap.

8. Special cases

Two team members click Take over

  1. Sarah clicks first → server sets mode human, agent = Sarah.
  2. Tom clicks a second later → server refuses: "Sarah is handling this chat".
  3. Tom can click Take over anyway (confirm) → agent = Tom. Visitor sees nothing new (same "Team member").

Team member closes the dashboard

  1. Their polls stop → agent_seen_at gets old.
  2. After 10 min, on the next visitor poll or message, server hands back automatically.
  3. Visitor sees "The AI assistant is back"; the AI answers the waiting message.

Visitor closes the tab

  1. Widget polls stop → away after 90 s, "Visitor left the page" after 3 min.
  2. Conversation ID was in the tab → gone for the visitor.
  3. Coming back later = a new tab = a new conversation. The old one stays in the Conversations log.

Visitor moves to another page (same tab)

  1. Conversation ID and messages stay in the tab (sessionStorage).
  2. Widget loads, polls, gets the current mode from the server.
  3. Takeover continues; nothing lost.

Takeover while the AI is still typing

  1. The AI answer already running finishes normally.
  2. The next visitor message goes to the team member.

Recording is off

  1. Nothing is saved, so no chat ever appears in Live chat.
  2. Widget never polls. Visitors get AI answers only.
  3. Live chat tab shows a notice: turn recording on to use live chat.
  4. Switched off during a takeover → open chats go back to the AI.

Better

  • One simple rule: one row = one bubble in the chat. Widget, dashboard and exports just list rows in order.
  • No special case for human mode: a visitor message is always visitor.
  • Easy to add new authors later (e.g. a "system" bot, WhatsApp channel).
  • Easy to add per-message things: 👍/👎 on ai rows, read receipts, attachments.
  • GDPR export/erase and CSV export are a plain row list.

Costs

  • Unanswered list and stats need a join: ai row (status dont_know) → its reply_to visitor row for the question text.
  • The "save question as pending, fill answer later" step becomes: insert visitor row, insert ai row pending, update it when done.
  • Every place that reads question/answer changes: logger, repository, Conversations tab, viewer drawer, Live chat, history builder.
  • Existing data must be converted (below).

How the switch would work (schema v5)

Convert old rows

  1. Add the new columns (role, content, reply_to).
  2. Each old qa row → one visitor row (the question) + one ai row (answer + AI details, reply_to = the visitor row).
  3. visitor, agent, event rows: copy text into content, set role.
  4. Done in batches (big logs), in id order, so chat order stays right.
  5. Drop question, answer, kind when every row is converted.

When to do it

  • Before the first public (commercial) release: after that, every customer site needs the migration.
  • Together with features that add per-message data (👍/👎 E1, GDPR export/erase, CSV export) so the code is changed once.
  • The takeover plan already keeps the switch small: kind rows map 1-to-1 to future roles, only qa rows split in two.

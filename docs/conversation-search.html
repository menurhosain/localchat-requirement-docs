How search works in a conversation

When a visitor sends a follow-up such as "yes" or "specification?", the question alone means almost nothing to the search. This page explains how the widget and server use the recent conversation to find the right sources, and why it was built this way.

Plugin: compact-local-chatbot · Written 2026-11-16 · Branch wwc-group-branding

1. The problem 2. Search vs. AI 3. Context text 4. Two searches, one list 5. Worked example 6. Why this design 7. Where in the code 8. Limits & next ideas

1The problem

The question is embedded and searched on its own. A follow-up carries no topic, so the search finds the wrong page (or nothing), and the AI never sees the right source.

AS105
AS105 is a flexible power cable series… silver-plated copper, silicone rubber, 200°C / 600V… Source [1] Flexible Power Cable
specification?
Sorry, I don't know the answer to that. Search matched "Tubular Braided Wire" (0.657), not AS105
AS105 specification please.
Conductor: Silver Plated Copper… Insulation: Silicone Rubber… Works only because the visitor repeated "AS105"
Two ways it failed. "Yes" matched nothing, so the gate stopped it before the AI. "specification?" matched the wrong page well enough (0.657 > min_score 0.5) to pass the gate, so the AI got Tubular Braided Wire sources plus AS105 history and answered "I don't know".

2What goes to search, what goes to the AI

History has two separate jobs. Mixing them up is the root of the problem.

Widget (browser)

  • Embeds the question
  • Builds + embeds the context text
  • Sends both, plus history (last N messages)
→

Search (server)

  • Question search
  • Context search
  • Merge → top_k sources
  • History is not used
→

AI prompt

  • System: rules + sources
  • History: last N messages, real roles
  • User: the question

Search needs: a short, focused topic

The recent turn only. Old topics and long text blur the match.

The AI needs: the whole thread

To know that "yes" answers "What would you like to know?". Controlled by the Conversation memory setting (history_messages, default 10, max 20).

  • Only finished turns count (answered or "I don't know"). Stopped, failed or interrupted answers are ignored.
  • No earlier turn, or Conversation memory = 0 → no context text is sent; the question is searched alone.
  • The widget embeds the context text only when the question itself got a vector (model loaded). Otherwise the context search runs on keywords. For API-provider indexes the server embeds it.
  • Sent as contextQuery + contextVector on POST /chat/ask. Both optional, so older cached widgets keep working.

4Two searches, one list (server)

AnswerService::run() runs both searches whenever a context text arrives. Each one goes through the normal gate (min_score) and source filter (source_min_score or top-3 keyword match).

Question searchContext searchResult
passespassesMerge both lists (below)
failspassesContext hits only
passesfailsQuestion hits only (as before)
failsfails"I don't know", no AI call

The merge: take turns, not scores

merge() picks one hit from each list in turn, skips chunks already taken, and stops at top_k. The list whose best meaning score is higher goes first, so its top hit becomes source [1].

Context search (goes first, higher score)

C1 · Flexible Power Cablechunk 3578
C2 · Flexible Power Cablechunk 3577

Question search

Q1 · Tubular Braided Wire0.657
Q2 · Tubular Braided Wire0.645

Merged, top_k = 4

[1]C1 Flexible Power Cable [2]Q1 Tubular Braided Wire [3]C2 Flexible Power Cable [4]Q2 Tubular Braided Wire

A chunk found by both searches is taken once (the second copy is skipped). Then PageExpander may send short pages whole, and the AI cites only the sources it uses.

Why turns, not scores? On this site, meaning scores sit close together (0.61–0.66) for right and wrong pages alike, so sorting by score cannot tell them apart. Taking turns guarantees each search gets its best hit in: a follow-up keeps the topic it follows, and a topic switch ("what about tubular braided wire?") keeps the page the new question names.

6Why this design

rejected Search with the whole conversation

  • Topic drift: AS105 → AS200 → "yes" still leans toward AS105.
  • Blurred vector: one embedding of 10 messages averages every topic.
  • Truncation: the model keeps the first ~512 tokens, which are the oldest messages.
  • Keyword noise: FULLTEXT with many words matches almost every chunk.

rejected Send history to the AI with no sources

The prompt says "answer only from the sources". With none, the AI either says "I don't know" anyway or makes up specs from memory. Made-up specs are worse for a product-spec bot.

tried first Context search only when the question fails

Fixed "yes" (no match → retry). It did not fix "specification?": the wrong page passed the gate, so the retry never ran. Replaced by always searching both and merging.

chosen Always both searches + take-turns merge

  • No extra AI call, no extra delay before streaming.
  • Standalone questions and topic switches keep their own top hit.
  • Cost: one more search on the server and one more embedding in the browser per follow-up.

When the search is right but the request is unclear

Good sources are not always enough. On the live site, "give me top 5" (after "Which AS105 size would you like?") reached the AI with a 0.76 match, yet the AI replied with the "I don't know" text. The visitor asked something vague; the AI had no other way out, and said_dont_know() logged it as "not answered".

The default prompt now has a rule right after the "I don't know" rule:

- Read short follow-ups (such as "yes" or "give me the top 5") in light of the conversation so far.
  If the request is still unclear, ask one short clarifying question instead of the text above,
  and suggest what you can answer from the sources. Do not ask when the sources simply lack the answer.

Before

which one is better?
I apologize, but I'm unable to determine the answer… logged as "not answered"

After (tested 2026-11-16)

which one is better?
The AS105 listings don't rate one size as "better"… If you share the part numbers or sizes you're comparing, I can list their specs side by side. logged as answered
Custom prompts don't get it. The rule is only in PromptBuilder::DEFAULT_TEMPLATE. A site with a saved custom template (Settings → Prompt) must have the line pasted in by hand. Also keep the "I don't know" text a plain "no answer" sentence: if it asks for clarification itself, the log can't tell "unclear" from "not in the sources".

Debugging a follow-up

wp db query "SELECT id, question, status, reason, top_score,
  JSON_EXTRACT(sources,'$.contextQuery') AS context,
  JSON_EXTRACT(sources,'$.sent') AS sent
FROM wp_mnaisp_messages ORDER BY id DESC LIMIT 5"
  • reason = model_dont_know → search passed, but the AI found nothing usable in the sources. Check found / sent.
  • reason = below_threshold / no_matches → both searches failed the gate.
  • contextQuery not null → the context search changed the sources.

8Limits & next ideas

  • top_k matters. On a follow-up the slots are shared between two searches. With 2, each search gets only 1. Dev site raised to 4 (default for new installs is 6).
  • min_score 0.5 is weak for bge-small: unrelated pages score ~0.65. Worth tuning.
  • Keyword-only mode: the context search on many words can bring loosely related chunks. The AI filters them, but they use slots.
  • Old cached widgets don't send contextQuery until the page cache refreshes. They behave like before.
  • Playground doesn't send a context query, so it tests single questions only.
  • Admin Conversations screen doesn't display contextQuery yet (stored, not shown).
  • Wrong citation number: in one test the AI answered about AS105 but cited [1] = AS155. Model mistake, not search; watch for it.
  • Next step if needed: AI query rewrite. A small AI call turns history + question into a standalone query ("AS105 specifications"). Best quality, but adds an extra call and delay. Could run only for short questions or ones with pronouns.

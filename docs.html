Knowledge Base Tables

How the plugin stores your pages, posts and files so the chatbot can answer from them.

Plugin: Compact Local Chat Bot & Knowledgebase · Last updated 2026-10-28

The big picture

The plugin uses two tables.

Resources

The list of everything in the knowledge base. One row is one page, one post or one file.

Chunks

Each resource cut into small pieces of about 250 words. Every piece has its own "meaning numbers" (embedding).

Think of a book. The resources table is the list of books. The chunks table holds the pages cut out of each book. Every page has a label that says which book it came from.

How the two tables connect

Every chunk stores the number of its resource in resource_id. One resource has many chunks. One chunk belongs to exactly one resource.

WordPress page (ID 42)  "Shipping Policy"
        │
        ▼
wp_mnaisp_resources
  id 7 · source_type post · source_id 42 · post_type page · status indexed · chunk_count 4
        │
        │  chunks.resource_id = 7
        ▼
wp_mnaisp_chunks
  id 101 · chunk_index 0 · "We ship to all EU countries…"   · [384 numbers]
  id 102 · chunk_index 1 · "Delivery takes 3–5 days…"       · [384 numbers]
  id 103 · chunk_index 2 · "Returns are free within…"       · [384 numbers]
  id 104 · chunk_index 3 · "Contact support at…"            · [384 numbers]

How the plugin uses this link

  • View chunks: show all chunks where resource_id = 7.
  • Re-embed: replace all chunks of resource 7 at once. The old chunks stay until the new ones are saved.
  • Page deleted: delete resource 7 and all its chunks.
  • Answering (phase 2): the search finds chunk 102. Its resource_id leads to resource 7, which gives the title and link for the citation "Shipping Policy".
No database foreign key. The database does not enforce the link. Our code keeps the two tables in step: it never deletes a resource without deleting its chunks. (WordPress's table tool and some cheap hosts don't handle foreign keys well.)

No link column. The link to a page or file is not saved. The plugin looks it up from source_id each time it is needed, so changing permalinks, a slug or the site domain never breaks citation links.

Keys

  • source_type + source_id is unique: the same page or file can't be added twice.
  • Index on status: finds queued, failed or outdated items fast.
  • Index on post_type: filters the list by Pages, Posts or a custom type fast.

Statuses

StatusWhat it means
queuedAdded and waiting to be processed.
processingBeing cut into chunks and embedded right now.
indexedDone. The chatbot can use it.
failedSomething went wrong. The reason is in error_message.
outdatedThe page changed, or the embedding model changed. The old chunks still work until it is re-embedded.
pausedThe page was unpublished (draft, private or trash). Its chunks are kept but the chatbot never uses them. Publishing it again brings it back, as indexed if nothing changed or outdated if it did.

"Not indexed" is not stored. Content that has no row in this table is simply not in the knowledge base.

Keys

  • Index on resource_id: finds all chunks of one resource fast.
  • Index on resource_id + chunk_hash: on re-embed, checks fast if an unchanged chunk already exists.
  • Full-text index on content: keyword search (phase 2). It finds exact words that meaning search can miss, like a product code "SKU-4471".

What goes into the model vs. what gets stored

Text sent to the model (not stored):
"Shipping Policy › Delivery times › Delivery takes 3–5 days…"
        │
        ▼  bge-small-en-v1.5
embedding column: [0.021, -0.113, 0.087, … 384 numbers]
  • Text sent to the model: title + heading + text. The model turns it into 384 numbers. The extra context makes search better: "Delivery takes 3–5 days" alone doesn't say what is delivered.
  • Only the numbers are stored in embedding. The column holds no text.
  • The text is stored separately: content has only the text ("Delivery takes 3–5 days…"), heading has the heading, and the title stays in the resources table. This keeps answers and citations clean.
  • The combined model text is never saved. It can be rebuilt any time from title + heading + content.
  • This is the same for the local model and for an API provider.

How chunk_hash is made

model key  = model name : revision : dtype : pooling : normalize
chunk_hash = sha256( model key + "|" + text sent to the model )

example:
sha256( "Xenova/bge-small-en-v1.5:ea104dac…:q8:cls:1|Shipping Policy › Delivery times › Delivery takes 3–5 days…" )
  • Same fingerprint means the same text and the same model, so the old embedding is reused.
  • The model key is only in the fingerprint. It is never sent to the model.
  • If the model changes, every fingerprint changes, so no old vector from a different model is ever reused.
  • The same goes for a new version (revision) or precision (dtype) of the same model, for example after a plugin update.
  • The server builds the model key and sends it to the browser, so both sides always use the same one.
  • If the title or heading changes, the fingerprint changes and the chunk is embedded again.

Setting: mnaisp_index_meta

A WordPress option (not a table). It remembers exactly how the chunks were embedded: model name, the exact model version (a fixed Hugging Face commit, so every browser downloads the same files), number of dimensions, model precision, pooling, normalizing, and the question prefix. If any of these changes (for example after a plugin update), all indexed items are marked outdated automatically.

Why it matters: in phase 2, visitor questions must be turned into numbers in exactly the same way. If any setting differs, the question's numbers won't match the chunks' numbers, and search gives bad results.
